# Reconstruction-stack research

## Decision

Build the MVP as a **local hybrid pipeline**:

1. `ffmpeg` is an external, pinned video-decoding tool.
2. `COLMAP` is an external, pinned *sparse-SfM* sidecar and owns the canonical
   calibrated, globally consistent camera trajectory.
3. The official `Depth Anything 3` (DA3) Python sidecar runs **pose-conditioned
   multi-view depth** over those frames and writes depth, confidence, and camera
   data in a documented interchange directory. Use `DA3-BASE` plus
   `DA3METRIC-LARGE` for an Apache-2.0 commercial-safe default. Permit
   `DA3NESTED-GIANT-LARGE-1.1` only as an explicitly non-commercial research
   backend; its checkpoint is CC BY-NC 4.0.
4. New, owned Rust code fuses the DA3 depth/confidence maps using the COLMAP
   camera trajectory into a confidence-weighted TSDF, extracts planes and a
   watertight floorplan mesh, and writes the final GLB and SVG.

This deliberately does **not** put a Rust FFI boundary around COLMAP, Open3D,
or Python. The Rust CLI owns orchestration, validation, data contracts, scale,
floorplan semantics, and exports; the two mature native/ML tools remain
replaceable command-line sidecars. The architecture is local-first: no image
leaves the machine after model weights and sidecars are installed.

## Why this is the selected stack

DA3 is specifically built for spatially consistent geometry from arbitrary
sets of visual inputs. Its official API accepts camera extrinsics and
intrinsics, in which case it runs pose-conditioned depth, and returns depth,
confidence, extrinsics, and intrinsics. Its official streaming implementation
is designed for long videos: it chunks images while carrying state and writes
per-frame pose/intrinsics and a combined point cloud. This is a much stronger
dense-depth source for indoor walls than treating unrelated monocular depth
maps as a reconstruction.

However, the streaming project explicitly says it is *not* an SLAM system. A
floorplan cannot silently accept accumulated trajectory drift. COLMAP is the
canonical tracking sidecar because it provides robust incremental SfM,
sequential matching designed for video (including vocabulary-tree loop
detection), camera calibration, and bundle adjustment. Supplying that
trajectory to DA3 gives the depth model a shared world frame; the DA3 poses
remain a diagnostic/fallback signal, never the authority for a released plan.

COLMAP's own dense PatchMatch/stereo-fusion path is retained as an optional
`--dense-mvs cuda` verification/enrichment mode, not a hard requirement. It
is excellent geometric evidence when the scene is textured, but introduces a
CUDA-heavy dependency and cannot be the only dense source for painted walls,
glazing, or low-texture corridors. The standard path therefore stays usable
without CUDA MVS while still requiring a CUDA-capable GPU for the selected DA3
backend.

The repository's Rust engine must not yet become the default DA3 sidecar:
`Engine::infer` is a single-image method and its own documents say several
real-hardware/end-to-end parity gates are still skipped or incomplete. Its
depth/confidence output is valuable future work, but it does not currently
offer DA3's batched, pose-conditioned video inference. Add a
`RustDa3Provider` only after it can produce the same frame-batch interchange
contract and passes agreement tests against the official Python backend.

## Concrete dependency boundary

| Responsibility | Selected owner | Boundary / durable output |
| --- | --- | --- |
| Probe and decode MP4/MOV, sample frames | `ffprobe` / `ffmpeg` executable | video metadata JSON; undistorted-or-original PNG keyframes and manifest |
| Camera model, global poses, loop closure | `colmap` executable | COLMAP sparse model plus normalized `cameras.json` (`K`, distortion, world-to-camera `T_w2c`, registration/reprojection diagnostics) |
| Dense multi-view depth and confidence | official DA3 Python environment | `frames.npz`/per-frame NPZ: RGB, `depth`, `confidence`, `K`, `T_w2c`, original pixel geometry; no GLB is consumed as source data |
| Metric scale | Rust `scale` module | a user-defined **3D reference segment** (two observed/tracked endpoints plus metres); one similarity scale applied to every pose, point, and depth |
| Fusion and floorplan extraction | Rust `floorplan-geometry` crate | sparse TSDF, point/normal samples, fitted floor/ceiling/wall planes, room polygons and mesh |
| Deliverables | Rust `floorplan-export` crate | standards-valid `floorplan.glb`, editable `floorplan.svg`, plus `report.json` |

`gltf-json` and `gltf` are appropriate small Rust export dependencies: the
former serializes the glTF JSON model and the latter has a GLB writer. SVG is
simple XML generated by the owned exporter, so it needs no graphics runtime.
The GLB uses metres (the glTF specification's default linear unit) and the
Z-up floorplan coordinate convention is stated in `report.json` and SVG
metadata.

### Required invocation flow

```text
video
  -> ffprobe + ffmpeg (frame sampling, sharpness/overlap selection)
  -> COLMAP feature_extractor -> sequential_matcher -> mapper -> bundle adjustment
  -> normalize COLMAP cameras/poses
  -> DA3 pose-conditioned batches (or DA3-Streaming for long sequences)
  -> reject low-confidence/out-of-consistency pixels
  -> apply the one anchored similarity scale
  -> Rust TSDF fusion -> planes/room topology -> mesh
  -> GLB + SVG + evidence report
```

The scale-anchor UI is not merely a number. It records a real-world length
*and the two endpoints of that segment* in the reconstruction (normally
selected in two or more keyframes and triangulated). A bare value such as
"4.20 m" cannot tell a reconstruction what geometry to scale.

## Alternatives considered

| Stack | Strength | Rejected limitation |
| --- | --- | --- |
| COLMAP end-to-end (sparse SfM + PatchMatch + fusion + mesh) | Mature all-local SfM/MVS and an excellent optional geometric verifier | Dense reconstruction is CUDA-heavy and stereo needs image texture; it does not robustly fill ordinary smooth indoor walls on its own. |
| DA3/DA3-Streaming only | Directly produces consistent multi-view depth, poses, confidence, combined PLY, and even a preview GLB | DA3-Streaming explicitly is not SLAM. Its predicted trajectory must not alone determine measured room dimensions. |
| Open3D RGB-D reconstruction sidecar | Provides scalable TSDF integration and marching-cubes mesh extraction | A second C++/Python runtime cannot use DA3 confidence weighting or floorplan topology without another boundary; it would make the core algorithm less inspectable and replaceable. |
| Existing Rust `da-engine` only | Reuses repository code and emits depth/confidence/intrinsics/extrinsics | Current public API is per-image and current E2E/native parity work is incomplete; it cannot guarantee a globally consistent walkthrough trajectory. |

## Implementation contracts and guardrails

- Pin sidecar container/image versions and checkpoint revision hashes in a
  `reconstruction.lock`; record them in every `report.json`.
- Treat coordinate transforms as typed data: camera `T_w2c`, camera centre,
  depth-unit, source image dimensions, and the global similarity transform
  travel together. Never infer a convention from a filename.
- The acceptance gate must fail before export if COLMAP does not form one
  sufficiently registered component, if loop/reprojection diagnostics exceed
  the ticket's limits, or if too little confident geometry remains after
  fusion. A preview can still be emitted with `--allow-preview`.
- Preserve intermediate `NPZ`, sparse model, selected frames, anchor, and
  quality metrics until the run is accepted. They make a wrong floorplan
  reproducible and debuggable.
- Do not market the DA3 NESTED/GIANT checkpoint as a production dependency:
  its model card is CC BY-NC 4.0 even though the code repository itself is
  Apache-2.0. The Apache-compatible default is `DA3-BASE` for any-view
  depth/pose plus `DA3METRIC-LARGE` for metric depth; the manual anchor
  remains the source of dimensional truth in either mode.
